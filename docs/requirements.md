# 要件定義書

## 背景・目的

生成AI・AI Agent・Multi Agent・RAG・AWS・SaaS・CI/CDを実際に設計・実装し、AI駆動開発の経験として説明できる状態にする。
題材として「冷蔵庫の食材から献立を提案するWebアプリ」を作る（アプリ自体の完成度より、技術要素の実装と説明可能性を優先する）。

## 対象ユーザー・ユースケース

- 個人（開発者自身）が使うSaaS想定のWebアプリ。将来的に複数ユーザーが使える設計にする。
- 主なユースケース：「手持ち食材を入力 → 条件（人数・時間・使い切り希望）を指定 → AIが献立・レシピ・不足食材を提案 → 履歴として保存」

## 機能要件

| 区分 | 内容 |
|---|---|
| 認証 | ユーザー登録・ログイン（MVPは自前JWT、将来Cognito移行） |
| 冷蔵庫管理 | 食材の登録・編集・削除（自然言語入力＋一覧編集） |
| 献立生成 | 条件（人数・調理時間・使い切り希望・好み・アレルギー）を指定してAIに献立を作成させる |
| 結果表示 | 献立名・使用食材・不足食材・手順・調理時間・難易度・食材消費率を表示 |
| 検証 | 献立が「存在しない食材」「矛盾する分量・時間」を含んでいないかAIが検証し、必要なら再生成 |
| 履歴 | 過去に作った献立の一覧・再表示 |

## 非機能要件

- **再現性・検証可能性**：Agentの入出力をログ化し、Hallucination対策（検証Agent）の効果を後から説明できること
- **セキュリティ**：APIキーはコードにハードコードしない、ユーザーデータは分離、最小権限のIAM
- **コスト**：AWS無料枠・LLM APIの低コストモデルを優先し、個人開発として課金を最小化
- **可搬性**：ローカル環境で完結して動作し、後からAWSへ無停止で移行できる構成にする（DBアクセスをORM経由にする等）
- **医療・栄養断定の回避**：栄養面の断定的アドバイスはしない（免責文言を出す）

## 制約条件

- `.env`等でシークレット管理、Gitにコミットしない
- 最初はローカルのみで完結させ、MVP完成後にAWS移行
- 各コンポーネントの設計意図を説明できる状態にする（面接等での説明を想定）

## MVPの範囲

**含める（v1）**
- Web GUI：食材入力／献立作成／結果表示／履歴（4画面）。ログインは自前JWT
- 4つのAgent：食材解析Agent・レシピ検索Agent（ローカルJSONキーワード検索）・献立作成Agent・検証Agent
- オーケストレーターによるAgent連携（検証NGなら献立作成Agentへ再生成、最大2回リトライ）
- DB：SQLite（ユーザー・冷蔵庫食材・履歴を保存）
- テスト：Agent単体テスト、RAG検索テスト、APIテスト
- GitHub：リポジトリ作成、README、CI（Lint→Test→Build）

**含めない（v2以降）**
- Embedding／ベクトル検索によるRAG高度化
- AWSへのデプロイ・Cognito認証・CI/CDでの自動デプロイ
- 本格的なマルチユーザー運用、画像認識による食材登録、栄養価計算
- LangGraph等のAgentフレームワーク導入
